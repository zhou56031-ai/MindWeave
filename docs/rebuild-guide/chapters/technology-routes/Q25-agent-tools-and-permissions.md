# Q25：Agent 工具白名单与权限边界

## 1. 原理与本项目的使用

第 48 篇把模型输出视作工具选择建议，而不是可直接执行的命令。服务端用限定工具名和专属参数模型再次校验；真正的 user_id 来自 JWT 依赖。读工具可立即查询当前用户数据，写工具先形成提案，到第 50 篇人工同意后才调用业务服务。这个边界可以阻止模型凭一段笔记里的恶意文字读别人的资料或写任意 SQL。[Pydantic 字段约束](https://docs.pydantic.dev/latest/concepts/fields/)。

## 2. 同类技术路线对比

| 路线 | 适合的情况 | 代价或边界 |
|---|---|---|
| 固定 Python 白名单 | 本项目少量确定工具，易审计 | 加工具需改后端代码 |
| 框架自动工具调用 | 工具多、编排方便 | 仍必须自行设计身份与写入批准 |
| MCP 等外部工具协议 | 跨服务复用能力 | 权限、凭据和数据外发边界更复杂 |
| 任意 Python/SQL 执行 | 研发沙箱中的受控实验 | 对普通用户数据风险过高，不适用 |

## 3. 工程边界与面试追问

工具参数中不接受 user_id、SQL 片段或任意 URL；服务内部用既有 NoteService、ReviewService，沿用原来的所有权检查。审批页面展示的参数快照要与服务器执行的快照一致，不能让浏览器批准 A 后换成 B。面试官会问提示注入如何处理：提示词只能减少模型偏离，真正保护靠工具白名单、输入校验、业务权限、审批和日志。
