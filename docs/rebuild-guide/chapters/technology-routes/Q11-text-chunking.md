# Q11｜为什么知识文档要切片？

> 说明：本篇解释第 23 篇的切片路线；具体实施状态以复刻代码与[教程目录](../../README.md)核对。

**对应位置：** [第 23 篇](../23-text-parser-and-chunks.md)计划新增的 `backend/app/services/document_parser.py`，其中 `split_text()` 采用每段 1000 字符、相邻段重叠 200 字符的固定窗口。

## 切片改变了什么

一份长文档整篇进入检索或模型上下文，容易占满可处理的长度，也不方便精确指出哪一段命中。切片把同一份文档拆成若干小段，保存时每段保留 `document_id` 和顺序，后续检索可以只拿相关片段。第 23 篇的窗口从位置 0 读到 1000，下一段从 800 开始；重复的 200 字符像相邻两张地图的交叠区域，减少句子恰好在边界被切断的影响。它**只产生文本片段**，没有自动生成向量、图谱或答案。

## 同类切片路线比较

| 路线 | 怎样决定边界 | 好处 | 需要付出的代价 |
|---|---|---|---|
| 固定字符窗口 | 按字符数推进，可设置重叠 | 规则简单、结果稳定、容易验证存储链 | 可能切断标题、句子或中文词语 |
| 递归结构切分 | 优先保留段落、换行、空格等较大单元，过长再细分 | 较容易保留文本结构 | 分隔符、语言和实际段长需要调试 |
| 按 token 切分 | 按模型 tokenizer 计数 | 更贴近模型上下文预算 | 与具体 tokenizer 绑定，字符数不再直观 |
| 按 Markdown 标题等文档结构 | 先按章节层级分组 | 易保留章节来源 | 超长章节仍需二次切分 |

LangChain 官方把这些列为不同策略，并说明递归切分优先保留较大的语义单元，重叠有助于缓解边界上下文损失。[文本切片策略](https://docs.langchain.com/oss/python/integrations/splitters)、[递归字符切片](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)

**本项目为什么先用固定窗口：** 第 23–24 篇先验证“文件 → 正文 → 切片 → MySQL”能稳定串起来；等检索阶段有固定问答样本，再比较不同切片策略对召回率和引用定位的影响。切片数变多不自动意味着答案更好，过度重叠还会产生重复候选。
