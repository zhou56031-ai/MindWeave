# Q19：Neo4j 知识图谱与关系型存储

## 1. 原理与本项目的使用

图谱把实体当节点、关联当边，适合从一个概念沿“相关/提及”走到相邻概念。第 39–44 篇用 Neo4j 存用户范围内的 Entity、Source 与关系，MySQL 仍是笔记和知识文档的权威正文。两种数据库不会共享普通事务，所以更新正文后登记图任务，再异步重建图。Neo4j 的 Docker 与 Cypher 文档分别解释部署和图查询。[Neo4j Docker](https://neo4j.com/docs/operations-manual/current/docker/introduction/)、[Cypher 手册](https://neo4j.com/docs/cypher-manual/current/)。

## 2. 同类技术路线对比

| 路线 | 适合的情况 | 代价或边界 |
|---|---|---|
| Neo4j 属性图 | 关系遍历、可视化、图查询直观 | 独立服务、同步、权限过滤与备份 |
| MySQL 邻接表 | 关系简单、现有 SQL 技术栈 | 多跳查询和关系类型演进复杂 |
| RDF/三元组库 | 需要本体、语义互操作 | 建模与查询学习成本较高 |
| 只用向量库 | 适合语义相似候选 | 难表达显式的有向关系与来源 |

## 3. 工程边界与面试追问

每个节点和边都带 user_id，并在路径的每一段限制用户；只在入口检查起点不够。实体名称归一化可减少重复，但误合并会污染图，必须保留来源和人工修订能力。面试官会追问 MySQL 成功、Neo4j 失败如何处理：答案是 MySQL 工单保持待处理/失败、Worker 重试、图查询显示状态，而不是谎称两库已强一致。
