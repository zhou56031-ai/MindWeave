# Q16：MySQL 字面匹配、全文索引、向量与图谱检索

第 35 篇先从复刻项目已有的 MySQL 笔记和知识切片中取候选。它使用带转义的字面 `contains` 条件，在 SQL 中限定当前用户，对结果做数量和长度控制，并携带来源 ID。这个版本能走通“用户问题 → 本人候选 → 有来源的上下文 → 模型回答”的最小闭环，却不会理解同义词，也不能用命中次数当答案可信度。[SQLAlchemy `contains` 与自动转义](https://docs.sqlalchemy.org/en/20/core/sqlelement.html#sqlalchemy.sql.expression.ColumnOperators.contains)

## 为什么先把权限写进检索 SQL

`Note` 自带 `user_id`，所以笔记查询直接过滤该列。`KnowledgeChunk` 没有用户列，它必须按 `document_id` 连接 `KnowledgeDocument`，再过滤文档 `user_id`。若先全库查切片，再只对前五条做 Python 过滤，已经可能把别人的正文读进内存、发给模型或写进日志。来源标题和文件名只负责显示，不能代替数据库归属判断。两账号同名同词的测试比用不同标题更能暴露权限错误。

## 同类路线比较

| 路线 | 擅长 | 弱点或增加的工作 |
|---|---|---|
| MySQL `LIKE` 字面匹配 | 数据量小、快速验证权限和来源链路 | 长自然语言问题召回弱；普通索引未必加速前导通配查询 |
| 数据库全文索引 | 词项查询、倒排候选、在库内排序 | 分词和中文支持需配置评估；同义改写依然有限 |
| Embedding 向量检索 | 相似语义表达、同义词相关性 | 模型与索引版本、维度、成本、权限过滤和重建都需维护 |
| 混合检索与重排 | 综合字面精确性和语义召回 | 链路更多，需离线评估集、融合权重和延迟预算 |
| 图谱检索 | 显式实体和关系、多跳路径 | 图谱抽取与同步复杂；边的来源、错误和用户隔离必须可追溯 |

## 当前上下文的实质边界

每类 SQL 候选限制 50 条，然后本地按字面出现次数取前五。它限制了一次请求的扫描结果和内存占用，但“先按时间取 50，再在 Python 排序”可能漏掉更旧、更相关的文本。`short_snippet` 最多截 800 个 Python 字符，`format_context` 再控制总字符量；字符数不是模型 token 数。若模型预算敏感，要用对应 tokenizer 估算或在上游拒绝超限时明确处理。[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)

来源标记帮助人和程序追查一段摘要来自哪篇笔记或哪份文档；它并不自动证明模型回答的每一句话都得到该来源支持。检索片段是用户可上传的数据，即使包含“忽略此前指令”也不能成为系统命令。第 36 篇把资料作为背景交给模型，并提示模型资料不足时承认不足。将来做严格引用，需要把回答断言和原文片段逐项对应并验收。

## 升级时如何证明更好

保留一组本项目测试问题、预期来源 ID、不能泄露的他人来源 ID，以及无命中和特殊字符问题。升级全文索引、向量或图谱时，对比召回率、用户隔离、延迟、成本和错误率，而不是只看一两个“回答变聪明”的演示。异步重建索引会出现数据库正文已更新、索引还没同步的窗口；必须定义状态、重试与回退策略。每条候选仍应能追溯原文与用户范围。
