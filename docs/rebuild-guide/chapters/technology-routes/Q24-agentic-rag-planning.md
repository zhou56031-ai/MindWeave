# Q24：Agentic RAG 查询规划与证据卡

## 1. 原理与本项目的使用

第 47 篇在检索前让模型把自然语言问题写成最多三个短查询，再按用户身份逐一检索，合并来源 ID，最后把证据卡交给回答阶段。模型只建议检索词，不决定 user_id，也不能把资料中的指令当系统要求。规划可能改善多概念问题的召回，同时增加一次模型调用和出错点；因此规划失败可退回原问题，权限检查不可退化。[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。

## 2. 同类技术路线对比

| 路线 | 适合的情况 | 代价或边界 |
|---|---|---|
| 单次直接检索 | 问题短、词项明确、成本低 | 复杂问题容易漏子主题 |
| 规则拆词 | 结构固定、费用低 | 语义变化时脆弱 |
| LLM 多查询规划 | 复杂问法、同义改写 | 耗时、费用、虚构检索词 |
| 迭代式 Agent 检索 | 多跳证据探索 | 循环和工具成本需严格上限 |

## 3. 工程边界与面试追问

证据卡应包括来源类型、来源 ID、标题和短摘要；这是可追溯线索，不保证回答每句话都有出处。对“无结果”“只命中别人的资料”“模型规划出错误实体”“多查询重复命中”建立固定测试。面试官若问为什么不无限循环检索，回答应涉及费用上限、时延、错误放大以及可评估性；本教程先把查询数锁在三条。
