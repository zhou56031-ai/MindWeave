# Q15：DeepSeek 模型客户端与同类接入路线

第 30–32、36 篇让后端以 DeepSeek 生成题目、补全、标签与聊天内容。密钥只在复刻后端的本机环境读取，前端只调用本项目 HTTP 接口。当前教程使用官方 Chat Completions 形状：向配置的基础 URL 下 `/chat/completions` 发送 `model`、`messages` 等字段，读取 `choices[0].message.content`；流式回答另读增量 `delta.content`。官方当前 API 文档是接口与模型名的最终依据，不要把教程里的示例名当永久常量。[DeepSeek API 文档](https://api-docs.deepseek.com/api/create-chat-completion/)

## 为什么把调用集中在客户端

回顾题、补全、标签和聊天的业务约束各不相同，但都需要同样的认证头、模型配置、超时和上游错误映射。集中客户端使路由不会复制密钥处理代码；业务服务负责判断用户有无权访问笔记，决定提示词、输入截断和结果验证。客户端只是外部边界，不是授权层，也不能证明模型回答正确。

HTTPX 的 `AsyncClient` 可在异步路由里等待网络响应，并提供连接、读取、写入和连接池超时。等待模型的期间事件循环能处理其他请求；这不意味着请求不用占用资源，仍需限制同时调用数、输出长度与费用。教程初版按请求短生命周期创建客户端，便于理解和关闭；高并发时可改为应用生命周期管理的共享连接池，并在关闭阶段调用 `aclose()`。[HTTPX 异步客户端](https://www.python-httpx.org/async/) · [HTTPX 超时](https://www.python-httpx.org/advanced/timeouts/)

## 同类路线比较

| 路线 | 适合什么 | 在此阶段的取舍 |
|---|---|---|
| 直接 HTTPX 调 DeepSeek | 需要清楚控制请求体、超时、错误和流式帧 | 本教程采用；代码较显式，协议变化需自己维护 |
| 官方 SDK | 希望减少协议样板，跟随官方接口 | 仍需业务层的权限、校验、日志遮蔽和失败策略 |
| OpenAI 兼容 SDK | 已有兼容抽象，想切换基础 URL | 兼容层不保证每个模型参数或返回细节完全一致，升级需验收 |
| LangChain/框架适配 | 多模型、多工具和复杂链路 | 后续 Agent 阶段可能更有用；当前三个小功能引入整套抽象会遮住关键 HTTP 边界 |
| 前端直接调用 | 原型看似省一个后端接口 | 浏览器会暴露密钥，且无法在服务器验证用户对笔记的权限；不采用 |

## JSON 模式为什么还要 Pydantic

DeepSeek 的 JSON 输出模式帮助得到可解析的 JSON 文本，仍需在提示里明确要求 JSON，也要处理空内容和截断。合法 JSON 不等于合法的业务对象：`{"choices":[]}` 依然不能当四选一题。第 31 篇用 `json.loads` 和 `ReviewQuestionResponse` 检查四个唯一选项与答案归属；第 32 篇用标签模型限制数量、长度和重复值。失败时保留原有数据库状态，不能把原始模型文本直接写入或返给前端。[DeepSeek JSON 输出说明](https://api-docs.deepseek.com/guides/json_mode/)

## 故障和费用的工程判断

缺密钥应让 AI 接口清楚失败，笔记和知识库仍能运行。连接错误、429、上游 5xx、协议结构变化要区分诊断；面向浏览器的响应不包含 Authorization 头、密钥或整段上游报错。超时并不证明上游未处理请求，因此计费调用不能无脑自动重试。若要安全重试，先设计请求幂等标识、预算限制和可观测日志。流式请求还要区分“收到几段内容”和“收到完整结束标志”：半途断开不应把局部答案记成成功对话。
