# Q13｜为什么多文件上传进度用 SSE？

> 说明：本篇解释第 25 篇的上传进度路线；具体实施状态以复刻代码与[教程目录](../../README.md)核对。

**对应位置：** [第 25 篇](../25-knowledge-sse-multi-upload.md)已提供 `POST /knowledge/add/multiple/stream`，返回 `text/event-stream`；复制来的前端 `useSSE` 使用 `fetch` 读取响应流，并解析每行 `data: {...}`。

## 一次 POST 怎样持续收到状态

浏览器先用一个 `FormData` 请求上传文件。服务端不等所有文件处理完才给一个 JSON，而是保持 HTTP 响应打开：每个文件先写 `processing` 事件，随后写 `completed` 或 `error`，最后写 `finish`。每条消息按 `data: ...` 加空行的流格式发送。这样页面可随服务端处理进展更新，而无需每秒另发一次查询。HTML 标准规定了 `text/event-stream` 的事件格式；本项目前端使用 `fetch` 解析同一种响应格式，**没有使用浏览器的 `EventSource` 对象**。[HTML 标准：Server-sent events](https://html.spec.whatwg.org/dev/server-sent-events.html)

流式响应已经开始后，不能再把单个文件失败改写成整个请求的 HTTP 422。第 25 篇因此用 `error` 事件报告该文件，并给每个文件独立数据库会话。一个文件成功后，后一个文件失败不会自动撤销前者；`finish` 表示这一批文件的处理流结束，**不等于向量或图谱已构建**。

## 与相似进度通信路线比较

| 路线 | 通信形态 | 适合什么 | 当前上传场景的取舍 |
|---|---|---|---|
| SSE 格式的 HTTP 响应流 | 服务端沿一个响应连续推送文字事件 | 上传后持续报告单向进度 | 前端已有 `fetch` 流解析，沿用接口即可 |
| 轮询 | 浏览器定时请求状态接口 | 任务可持久化、客户端可能断线重连 | 需要另建任务 ID 与状态存储；对短上传多一次设计 |
| WebSocket | 建立可双向传消息的连接 | 长时双向交互、客户端需频繁实时指令 | 本篇仅单向报告文件进度，暂不需要双向通道 |

**本项目的边界：** SSE 连接断开后，已提交的文件不会因为前端没收到 `completed` 就自动回滚；页面要靠重新请求文档列表核对真实结果。真正的后台任务、断线恢复和任务状态持久化留待后续阶段。
