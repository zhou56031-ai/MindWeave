# Q33：分批索引、暂存标签与代际发布

> 对应第 69 篇的 chunk_index 与 Worker 改造。这里只说明计划路线；正式项目尚未按本篇重建索引。

## 1. 原理：完整构建后再发布

把一次来源索引升级想成图书馆换目录：新目录还没有整理完时，读者继续使用旧目录；全部整理好，再将新目录作为正式版本。

`chunk_index.replace_chunks` 给一次来源构建分配 generation，将所有片段分批嵌入，并写成 `ChunkStaging` 节点。现有向量和全文索引针对 `Chunk` 标签，暂存节点不会通过这两个正式索引成为普通结果。模型嵌入等待期间不持有整个 Neo4j 写事务。

每批结束，Worker 的 index_progress 回调把处理片数写回 MySQL，并检查 GraphTask.run_token。全部完成后，再通过一个 Neo4j 事务删除旧 Chunk，把本代暂存节点切为 Chunk。发生普通错误时，清理本代尚未发布的暂存，不删除旧正式索引。

Neo4j 事务为同一次事务内的变更提供共同提交或回滚边界，但 MySQL 的任务进度不在这个边界里。第 69 篇没有跨数据库分布式事务，也没有把此设计写成“所有系统同时原子更新”。[Neo4j Python Driver Transactions](https://neo4j.com/docs/python-manual/current/transactions/)

来源的正文哈希与切片版本承担不同职责：哈希说明内容是否变化，CHUNK_VERSION 说明切法是否升级。正文不变但版本变了仍需要重新索引。新任务与旧 Worker 的令牌比较用于阻止明显过时的构建，不能完全消除跨库最后检查后的竞争窗口。

## 2. 同类技术路线对比

| 路线 | 适用情况 | 优点 | 代价与风险 |
|---|---|---|---|
| 删旧后逐批写新 | 允许短时不可用的小型离线维护 | 实现最简单，占用额外空间较少 | 中途失败只剩部分新数据，查询可能看到不完整来源 |
| 全部向量先留内存，再一个事务替换 | 文档规模小、向量数量可控 | 写入边界清晰 | 内存随来源大小增长，嵌入失败前没有持久进度 |
| 本篇暂存标签 + 来源级发布 | 希望保留旧结果、又需要分批嵌入 | 中途失败不混入半成品，复用当前 Neo4j | 暂存占空间，激活仍需来源级事务，崩溃遗留需要维护 |
| 活跃版本指针 + 多代正式数据 | 需要频繁更新与快速回滚 | 发布可主要更新指针，容易保留上一代 | 所有查询都必须严格过滤活跃代，垃圾回收和索引过滤更复杂 |
| 独立索引/集合重建后切别名 | 支持集合或索引别名的检索系统 | 适合整库重建和蓝绿发布 | 占用双份索引资源，通常需要新的基础设施能力 |

本篇没有更换现有向量存储，只升级原有 Neo4j Chunk 写入方式。索引仍以标签和属性定义，部署版本与索引可见性需按实际环境判断，不把最新文档中的新查询语法直接引入现有 5.26 配置。[Neo4j Vector Indexes](https://neo4j.com/docs/cypher-manual/current/indexes/search-indexes/vector-indexes/)

## 3. 工程边界与面试关注点

**第 20 批失败后会接着第 21 批吗？** 当前不会。进度用于观测与取消旧任务，普通失败清理本代暂存，下次重新构建整代；尚未设计每批校验与恢复水位。

**进程被强杀怎么办？** finally 不保证执行，可能遗留 ChunkStaging。正常查询仍不会通过正式索引读到它们，但磁盘会增长，需要按构建代与时间清理。不能把 Python finally 当成崩溃恢复机制。

**两个 Worker 更新同一来源是否完全安全？** 常规领取受 MySQL 行锁和运行令牌保护，分批回调再次检查。由于 MySQL 检查和 Neo4j 发布分离，最后检查后若发生新编辑仍可能短暂发布旧内容；后续新任务覆盖。需要更强语义时应引入来源版本围栏、统一发布协调或调整存储边界。

**为什么不能直接批量重建所有用户？** 全量会消耗真实嵌入与抽取额度，并影响运行队列。教程给按用户名显式登记、每页 50 条来源的维护入口；操作由用户决定，本次没有执行。

**旧文档为什么没有自动变成新切法？** Worker 对旧文档使用已保存的 KnowledgeChunk，避免错误重建页号和覆盖原始业务记录。它能补齐全部既有片段的索引，新结构切法对新导入内容生效；历史文档重新解析属于另一项迁移。
