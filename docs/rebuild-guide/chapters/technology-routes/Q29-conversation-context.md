# Q29：对话记忆与上下文整理，为什么存了历史还不够

## 1. 原理：把保存的材料变成这一轮真正可用的输入

对应操作教程：[第 66 篇](../66-ai-conversation-quality.md)。本篇解释即将引入的有限历史窗口与显式证据交接，不表示正式应用已经完成修改。

数据库里的聊天记录像档案柜；模型这次接到的 messages 像开会时桌上的材料。档案柜里保存了十页，不代表桌上就有十页。要让模型理解“第二个为什么快”，程序必须把之前讨论 MySQL 和 Redis 的消息主动放到桌上。

第 66 篇的 `ChatSessionService.history_for_model` 负责在当前用户范围内读取最近 12 条记录，`bounded_history` 负责保留最多六个问答轮次、按字符限制长度，`answer_messages` 再把系统规则、历史消息和当前问题组合成最终输入。历史同时交给 `workflow.choose` 和 `collect_evidence`，因此工具决策和检索规划也能理解指代，不只是最后回答看见历史。

这一设计复用应用已有的消息表，以应用查询作为对话历史来源。它没有把普通数据库消息自动转换为 LangGraph 的消息状态。框架式短期记忆通常把消息放入 Agent 状态，通过 checkpointer 持久化；状态里需要有实际消息，模型调用时也需要使用这些消息。[LangChain 短期记忆文档](https://docs.langchain.com/oss/python/langchain/short-term-memory)说明了消息、状态与会话持久化的关系。

本轮工具观察又是另一种材料。`observations` 记录本轮查到的统计、回顾等事实；`none` 只是停止决策。把最后一个状态当作全部结果，就像会议结束时把“散会”当作会议结论。第 66 篇使用 `tool_evidence` 汇总有效读工具结果，写入提案仍走审批流程，不能算已执行事实。

这里的记忆是提供上下文，不是训练模型。换了模型服务也要传历史；更换 API key 不会自动修复历史漏传。

## 2. 同类路线对比：什么时候用窗口、摘要或检索

| 路线 | 怎样组织历史 | 优势 | 代价与适用边界 |
|---|---|---|---|
| 最近完整轮次窗口 | 查询最近若干消息，按轮次和预算裁剪 | 改动小、原话保真、容易复现 | 较早信息会丢失，适合当前项目的近期追问 |
| 全量历史 | 每轮发送会话全部记录 | 实现直观，短会话内容完整 | 输入不断增长，旧信息可能干扰当前任务，不适合无限聊天 |
| 滚动摘要加近期原话 | 旧消息压缩成摘要，近期消息保留原文 | 能保留更长时间范围的背景 | 摘要会丢细节或固化误解，需要版本与纠错设计 |
| 历史检索 | 根据当前问题，从历史片段或长期记忆中选择内容 | 适合跨话题和长期偏好 | 可能检索不到，必须按用户隔离，并处理过期记忆 |
| 框架消息状态 | Agent 状态直接维护 messages，checkpoint 保存执行状态 | 对工具消息、恢复和图执行更统一 | 要统一现有消息镜像和状态的职责，避免双份历史不一致 |

本项目先选择窗口，是因为现有 SQLAlchemy 会话表已保存成功轮次，改动能够直接针对当前缺陷。不是因为框架状态或摘要不好。原项目使用历史转换后交给 Agent 的方式；第 66 篇也主动读取历史，但继续沿用复刻版自定义工具图和 HTTP 客户端，没有声称完全复制原项目。

窗口裁剪应该同时考虑条数、长度和完整性。六轮都很长时，仅限制轮数仍会产生很大的请求；只截最后几千字符，又可能从半句开始。当前实现优先保留完整角色配对，每条消息最多 3000 字符，总历史最多 12000 字符。它是容易理解的第一版限制，精确 token 预算和语义摘要尚未实现。

## 3. 工程边界：记住更多，不等于相信更多

**权限边界。** 先检查会话归属，再取消息。前端传来的 session_id 只是定位信息，不是授权。数据库异常时本轮明确失败，不能回退成读取所有人的最近消息。

**事实边界。** 旧助手回答可能有误，也可能在工具执行前描述了一个计划。它只能帮助理解语境，不能作为本轮数据库状态、实时新闻或操作成功的证明。工具结果和检索内容也可能包含指令性文字，因此提示词要声明数据边界，真正的写操作仍靠后端校验和审批。

**资源边界。** 第 66 篇先在短数据库会话中读取历史，然后关闭这个会话再等待模型。AsyncSession 包含事务状态，并发任务需要各自的会话；不能为了共享历史把一个会话对象传给多个同时运行的任务。[SQLAlchemy 异步会话文档](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks)对此有明确说明。

**并发边界。** 当前消息表没有单独的轮次编号。本篇依赖已有的成功轮次成对写入和消息 ID 顺序。同一会话的并发请求可能使用相同旧历史，工具图状态也可能相互覆盖。本篇没有完成会话级串行化，不能把读历史的单元测试通过理解成多实例并发已验证。

**质量边界。** 自动测试应捕获模型实际收到的 messages，验证历史和工具事实是否存在，而不只是断言“接口返回 200”。然后用相同资料、相同问题做真实回答对照。模型返回自然语言有不确定性，重点判断指代、依据和解释是否正确，不比较每一个字是否一致。
