# Q07｜为什么密码要用慢哈希，而项目用 bcrypt？

**对应位置：** `backend/app/services/user_service.py` 中的 `pwd_context`、`hash_password()`、`verify_password()`；接入步骤见[第 07 篇](../07-user-model-registration.md)。本篇是密码存储技术路线，与 JWT 登录令牌不是同一件事。

## 注册和登录各发生什么

注册时，用户提交明文密码，服务调用 `hash_password` 产生带算法参数和盐信息的哈希结果，再把哈希写入用户表。登录时，服务从表中取出哈希，用 `verify_password` 对提交的密码做校验；不需要、也不应该把哈希“解密”成原密码。比喻成门锁更容易记：数据库保存的是可检查钥匙是否合适的锁芯信息，而不是备用钥匙。

密码不能用普通 SHA-256 或 MD5 直接存储：它们计算太快，泄露后攻击者可以高频猜测。密码哈希需要可调节成本，通常还要为每个密码使用独立盐。OWASP 当前建议新设计优先考虑 Argon2id；bcrypt 与 PBKDF2 也有各自的兼容或合规场景。[OWASP 密码存储建议](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

## 同类算法怎么选

| 路线 | 主要特征 | 适用判断 | 本项目情况 |
|---|---|---|---|
| Argon2id | 可调内存、迭代和并行参数 | 新系统选型可优先评估 | 参考实现未采用，本教程不在复刻中擅自替换 |
| bcrypt | 有成本参数，历史系统中很常见 | 与既有密码哈希格式兼容时 | 当前使用 `passlib` 的 bcrypt 配置 |
| PBKDF2 | 以迭代次数增加计算成本 | 有特定合规要求时评估 | 当前未使用 |
| 直接 SHA-256 / MD5 | 快速摘要算法 | 文件指纹等其他用途 | 不用于存储用户密码 |

**项目边界：** 当前沿用 bcrypt 是为了保持参考项目的身份链路。以后如果要升级算法，需要设计旧哈希验证与登录后重哈希策略；不能直接改算法后让已有账号全部失效。账号密码为 `123`、`456` 的练习账号只用于本机复刻验证，不能代表合理的真实用户密码策略。
