# Q30：Agent 循环与可恢复的上下文压缩

## 1. 原理：让模型继续工作，而不是只回答一次

对应 [第 67 篇操作教程](../67-agent-loop-and-context-compaction.md)。参考项目是 [learn-claude-code](https://github.com/shareAI-lab/learn-claude-code/blob/ce8f9f186058939da54c9d6fead78dfb5d0fd6c3/README.md)，本次固定提交 `ce8f9f186058939da54c9d6fead78dfb5d0fd6c3`，主要借鉴 [s01](https://github.com/shareAI-lab/learn-claude-code/blob/ce8f9f186058939da54c9d6fead78dfb5d0fd6c3/s01_agent_loop/code.py) 的循环与 [s08](https://github.com/shareAI-lab/learn-claude-code/blob/ce8f9f186058939da54c9d6fead78dfb5d0fd6c3/s08_context_compact/code.py) 的压缩机制。旧版压缩对应 s06，当前主线对应 s08。以下 RAGNotebook 代码是适配实现，并不直接复用参考项目的 bash、文件写入或终端权限。

模型并不会因为数据库里有历史，就自动读取；也不会因为程序叫 Agent，就自动反复查资料。`chat_loop.run_loop` 每轮显式发送当前 messages 和工具定义。模型返回工具调用时，服务校验参数、执行读工具、追加调用记录和结果，再发起下一轮。没有工具调用而返回最终文本，才完成这个循环。DeepSeek Chat Completions 使用 `tool_calls` 与带 `tool_call_id` 的 tool 消息承接这条链。[官方工具消息契约](https://api-docs.deepseek.com/api/create-chat-completion/)提供了这些字段的定义。

工作上下文像一张有限大的桌子。MySQL 原始聊天和 chat_artifacts 是档案柜；压缩摘要是交接卡。大工具输出先放进柜子，桌上留预览和编号；旧输出已经消费过，就用短编号替代；桌面仍放不下时，才总结较早轮次。需要精确内容时调用 read_artifact 按页取回。第 67 篇的 AgentContext 用真实 user 消息划分轮次，切口不跨越 assistant/tool 配对。

参考项目 s08 将持久化大输出、结构裁剪、旧结果缩减和最终摘要组织成渐进处理，并提供一次长度拒绝后的恢复。本项目保留归档、旧结果缩减、摘要、主动 compact 与一次失败恢复，但不照搬其中固定消息数 snip：这里直接以近期完整轮次为摘要边界，原文转入数据库归档。不是每次多几条消息都调用一次摘要模型，也不把被丢弃的句子当成已经“压缩”。

摘要保存目标、约束、事实、已完成事项、未解决问题和来源。它只作为参考数据传入，不能提升成系统指令。写提案不算已完成事项，旧助手回答不自动算工具事实。这里的“知识压缩”只针对会话工作上下文；它不会重新训练模型或替换知识库文档。

## 2. 同类路线对比

| 编排路线 | 模型怎样继续 | 优势 | 代价与本项目关系 |
|---|---|---|---|
| 固定检索后回答 | 程序预设一次检索，然后生成 | 行为简单，容易限制耗时 | 对新发现的问题缺少补查空间；原聊天入口接近此形式 |
| 自定义 JSON 决策循环 | 模型输出 tool 名，程序手工整理观察 | 容易兼容普通文本模型 | 协议、停止条件和观察交接全由应用维护；旧 workflow 属于这种路线 |
| 原生工具消息循环 | 模型返回 tool_calls，结果以 tool 消息回传 | 模型能继续消费同一消息链；工具关联明确 | 必须保证调用与结果配对，处理不合法参数、预算与审批；第 67 篇采用 |
| 图式编排与 checkpoint | 状态图定义节点、分支和恢复 | 适合复杂流程及持久中断 | 需要把 messages 和状态真正接入模型；安装 LangGraph 本身不等于已有记忆 |

使用 while 或 for 都能实现 Agent 循环，关键在于“新的工具结果是否进入下一次模型决策”。第 67 篇用有限次数 for，目的是让退出边界明确，机制上仍是模型和工具反复交互。它没有引入新的框架依赖。

| 压缩路线 | 保留什么 | 适合什么 | 主要问题 |
|---|---|---|---|
| 固定窗口截断 | 最后若干条原话 | 短会话、临时问答 | 较早约束可能彻底消失，没有恢复索引 |
| 归档加预览 | 原文完整保存，活跃输入只放摘要式预览与 ID | 大工具结果，偶尔需要精确回读 | 多一次存储和回读，需严格用户范围及保留期 |
| 滚动结构化摘要 | 旧目标、事实和约束压缩，近期原话保留 | 长会话继续讨论 | 有损且可能失真，需要原文与质量验证 |
| 历史检索或长期记忆 | 只召回当前相关片段 | 跨话题、跨会话偏好 | 检索可能漏掉，必须设计来源、过期和纠错 |
| 服务端上下文管理 | 服务提供商维护或压缩状态 | 使用特定托管 API 的应用 | 依赖服务契约、成本和可观测性，不等于本地库自动获得记忆 |

本篇选择“归档＋旧结果缩减＋摘要”，因为现有 MySQL 和 Redis 可以承担持久化与串行化，并能明确解释信息去了哪里。既不把长对话全部塞给模型，也不要求马上引入向量记忆库。长期用户偏好不是本篇目标，不能把 s08 压缩当成 s09 长期记忆的全部实现。

## 3. 工程边界与验证标准

**协议边界：** 原生工具调用必须有对应结果。新的客户端保留 tool_calls，循环用相同 ID 回传；压缩按完整轮次处理，不从工具结果中间开始下一次请求。每轮只允许一个调用，超出时明确报协议异常。第三方兼容通道是否真正支持 tools，仍要实际验证。

**预算边界：** 字节估算是本项目的早期保护，不是精确 token 计数。系统提示、工具描述、摘要和消息都计入；模型输出、网络时间和摘要调用另有限制。一次长度拒绝可以触发强制压缩，第二次停止；不以无限重试掩盖当前任务本身过大。

**持久化边界：** 原始问答与 agent_context 水位线在同一事务提交；完整工具输出和快照先独立归档。压缩失败不会覆盖原摘要。归档可能包含用户私有内容，读取必须同时限定 artifact_id、user_id、session_id，删除会话时跟随清理。会话列表过滤内部工作台，避免无意义地传输所有上下文。

**并发边界：** Redis 租约覆盖普通聊天和审批恢复。租约有 TTL，总运行时间比 TTL 短；进程崩溃后等待过期，不删除其他执行者的令牌。极端暂停和网络分区仍存在风险，严格多实例系统应进一步引入 fencing/version 检查与一致性验证；本篇不把简单租约宣传成完备的分布式事务。

**审批边界：** 模型只能提出写操作。审批卡、AgentRun 和原有写服务继续负责执行；新循环遇到提案就停止，不把待执行工具保存成已完成事实。审批之后当前实现不自动续跑旧循环，下一轮从已保存的问答继续。

**质量边界：** 摘要 JSON 合法只说明结构对，不能证明事实没丢。应固定测试包含约束、纠正、失败工具和来源的长对话，检查压缩后是否保持目标与未完成事项；精确引用必须能从归档回读。第 67 篇的 25 项新增离线测试验证协议、恢复与边界，加上相关旧测试共 46 项；真实模型是否少检索、正确补查以及费用是否可接受，仍需要按操作教程做同题评估。
