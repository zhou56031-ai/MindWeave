# Q31：Agent 诊断、ContextVar 与调用追踪

> 对应第 68 篇。本文解释计划引入的路线，应用代码尚未按本篇修改；没有执行测试、采集用户请求或生成效果数据。

## 1. 原理：为什么需要请求级过程记录

一个聊天请求会嵌套调用模型、检索规划、可答性判断、工具、摘要与数据库。只记 HTTP 请求总耗时，无法判断慢在何处；只把工具开始写在终端里，也很难区分两个同时发生的会话。

第 68 篇计划使用三层标识：会话 ID 表示长期对话，trace_run_id 表示一次用户请求，span_id 表示其中一段操作。审批表 agent_runs.id 继续表示一次待批准的业务运行，不能与诊断编号混用。

`app/core/agent_trace.py` 的 TraceBuffer 收集事件，span 在进入、退出和异常时记录状态与耗时。以单调计时的 perf_counter 计算持续时间，数据库 created_at 则表示保存时的日历时间，二者用途不同。

一次 RAG 工具可以对应如下父子关系：

```text
agent.tool
  rag.collect
    llm.http（查询规划）
    rag.rerank（第 69 篇后引入）
      llm.http（相关性排序）
    rag.select
    llm.http（可答性）
```

`ContextVar` 让深层函数取得当前请求的 TraceBuffer，并在退出绑定后恢复先前状态，避免普通全局 current_run_id 被并发请求覆盖。Python 文档明确说明上下文变量用于上下文局部状态，并支持 asyncio 场景；第 68 篇采用 Python 3.12 可用的 set/reset 方式。[Python 3.12 Context Variables](https://docs.python.org/3.12/library/contextvars.html)

ContextVar 传递的是对象引用，不会复制整份诊断；子任务继承上下文后可能共用同一缓冲区。事件通过序号和父 span 组织，但这个设计不自动形成跨进程协议，也不等于已经接入 OpenTelemetry。OpenTelemetry 将 Trace 组织为有关联的 Span，是后续导出时可参考的通用模型。[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)

HTTP 记录保存在 `model_trace_http.post_model`，能看到每次主备尝试的 key_slot、状态、耗时和实际 usage，不保存请求头。文本默认保存长度和 SHA-256，显式开启后才保存最多 400 字符预览。工具原文仍在已有 chat_artifacts，诊断只记录 artifact_id，避免重复复制全部材料。

usage 来自供应商响应，缺失就缺失；输入字符数不是 token 数，token 数也不是金额。DeepSeek 的接口返回 usage 与结束原因，本章读取这些字段而不额外发起计费查询。[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)

## 2. 同类技术路线对比

| 路线 | 适用需求 | 优点 | 代价与边界 |
|---|---|---|---|
| 普通结构化日志与请求 ID | 少量 API，主要排查错误 | 简单、已有日志系统容易接入 | 嵌套关系与模型实际材料需自行组织 |
| 本篇 ContextVar + 有界事件 + MySQL | 本机学习项目，希望看清整个 Agent 请求 | 复用已有数据库，代码路径明确，便于按用户过滤查询 | 请求内存收集、结束时尽力落库，进程崩溃可能丢失 |
| OpenTelemetry SDK + Collector + Trace 后端 | 多服务、多实例、跨系统追踪 | 有统一传播和导出体系，便于关联基础设施 | 增加依赖、服务和运维，需要设计采样与数据控制 |
| 面向 LLM 的观测平台 | 需要调用分析、提示词版本与效果管理 | 常有模型过程展示和产品化查询能力 | 接入方式、存储位置、成本和权限需要单独确认 |
| 持久事件表/队列逐步写入 | 请求中途也要求强恢复或审计记录 | 不必等请求结束才保存过程 | 写入量与一致性设计更复杂，业务重放不能仅凭日志完成 |

第 68 篇选用应用内缓冲与 MySQL，是为了先掌握请求关联、父子阶段、实际证据和失败状态；相对原复刻项目，这是求职准备阶段新增的诊断能力，并非为追求参考项目逐项一致而照搬。

后续改用观测平台时，可以保留 span 的业务边界与字段语义，更换事件导出方式。不要让每个业务函数同时绑定两套不同的“当前请求”全局状态。

## 3. 工程边界与面试关注点

**记录会不会影响业务？** 有事件数和单事件大小上限，保存独立于业务提交且有截止时间；仍有序列化与数据库成本。达到上限要显示 dropped，而不是声称记录完整。请求结束后保存不提供崩溃前数据保证。

**为什么状态可能有两种解释？** HTTP 200 只表示模型接口返回成功；模型内容仍可能格式不对。工具函数也可能返回 error 字典而不抛异常，因此分别记录 HTTP、协议阶段和 business_error，避免把传输成功等同于任务成功。

**诊断是否会泄露数据？** 默认不存正文，也不存 Authorization 或完整异常字符串；但是 ID、文本指纹和显式开启的预览仍需要用户范围过滤与保留期。哈希不是加密，低熵文本可以被猜测，不能写成“绝对匿名”。

**为什么删除会话后可能还有记录？** 诊断没有外键，能记录会话创建前的失败。删除时主动清理已有记录，但并发中的结束落库可能晚于删除，剩余记录由保留期回收。规模扩大后应补单独的清理作业与更明确的数据生命周期。

**如何用于面试？** 沿一次真实请求说明“计划查什么、召回什么、送入模型什么、最终保存什么”，并用事件证明问题发生在哪个边界。不能仅凭有 Trace 就声称准确率或性能已经提高。
