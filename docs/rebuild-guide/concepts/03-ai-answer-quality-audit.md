# 为什么原项目的 AI 更灵活，复刻版回答更机械

## 1. 对比结论与范围

本次检查日期：2026-10-21。参考项目是仓库根目录的 `backend/`，复刻项目是 `RAGNotebook-rebuild/backend/`。本次只检查和解释，没有修改业务代码，也没有执行已取消的第 37–39 篇任务。

两套本地 `.env` 配置的聊天模型名称都是 `deepseek-flash`，嵌入模型名称都是 `text-embedding-v4`。这只能证明文件配置的模型名称一致，不代表已经确认运行进程读取了同一配置、调用了完全相同的服务，或拥有相同的资料。

当前最确定的问题是：复刻版没有把历史聊天传给回答模型；正常结束工具循环时会丢失最终回答需要的工具结果；所有问题都被限制为仅依据检索资料回答；回答输出预算偏小。这些问题足以解释追问接不上、查到结果却答不出、普通问题回答拘谨等表现。

复刻版已经具备图检索、向量和全文混合检索、可答性判断、联网搜索实现、多工具循环和 checkpoint。不能继续把它描述为“只有关键词搜索”或“只能调用一次工具”。旧审计文档中相关缺失项已落后于当前代码。

| 环节 | 原项目当前代码 | 复刻项目当前代码 | 影响 |
|---|---|---|---|
| 历史对话 | 读取会话历史，拼入模型消息 | 保存历史，但最终回答只传系统要求和本轮问题 | 模型不知道“它”“第二个”“继续”指什么 |
| 工具结果 | 工具消息参与 Agent 后续决策和回答 | 决策能看到 observations，最终回答仅使用最后的 tool_result | 结束时结果可能被覆盖成空 |
| 普通知识问答 | 没有参考资料时，主提示词允许使用模型已有知识 | 所有问题都要求仅依据来源回答 | 没有资料时容易机械地说无法回答 |
| 补充检索 | Agent 可调用 search_rag 从新角度补查 | 固定检索完成后直接生成，回答模型未绑定工具 | 回答阶段发现缺口也不能主动补查 |
| 输出预算 | 对话模型构造处没有显式设置 700 token 上限 | 流式回答默认最多 700 token | 长解释可能截断并返回错误 |
| 检索决策 | 计划包含是否检索、检索工具等 | 计划只生成 1–3 个查询，固定执行检索流程 | 简单聊天也会绕一轮资料检索 |

## 2. 数据具体在哪些地方断开

### 历史记录存进了数据库，但没有放进模型的书包

原项目 `backend/app/agent/agent.py` 的流式入口调用 `get_history(session_id, user_id)`，再把历史转换成消息，最终发送：

```python
inputs = {"messages": [*chat_history, HumanMessage(content=query)]}
```

复刻版 `RAGNotebook-rebuild/backend/app/services/chat_stream_service.py` 在回答结束后调用 `append_turn` 存储对话，但生成回答时构造的 `messages` 只有系统提示词和当前问题，没有读取旧消息。

比如第一轮你说：“比较 MySQL 和 Redis。”第二轮你说：“第二个适合存什么？”界面虽然显示了第一轮，模型却只拿到“第二个适合存什么”。这就像老师把上一页讲义收进档案柜，却只给学生发了写着“解释第二个”的新纸条。数据库保存成功和模型能利用记忆，是两条需要分别接通的数据流。

checkpoint 也不会自动补齐这件事。复刻版工具图状态里没有对话消息列表，而且每次请求都会重置 observations；最终回答更是单独调用另一个模型接口。

### 工具查到了答案，交卷时却把草稿擦掉了

复刻版 `app/agent/workflow.py` 会反复选择工具，将结果保存在 observations。可是 `resolve` 每次都会更新 `tool_result`。

实际模拟了以下过程，不调用真实模型、不连接数据库：

```text
用户：今天回顾什么？
第一次选择：today_reviews
工具返回：note-demo | 学习事务
第二次选择：none，表示已经完成工具查询
none 对应的 read_tool 返回：None
最终 tool_result：None
observations：仍然保存着“学习事务”
```

聊天服务只读取 `decision.get("tool_result")`，没有把 observations 交给最终回答模型。因此模型收到的是“工具读取结果：无”。

像一位助手已经查完登记册，也在工作日志里记下了答案，交接时却只递出最后一张写着“无需继续查询”的纸。问题出在交接：查询确实完成了，但回答者没有得到查询结果。单纯把工具循环次数调大不能解决这个问题。

### 提示词把“基于资料回答”应用到了所有问题

复刻版统一要求：“仅依据给出的来源回答；资料不足时明确说没有找到可靠依据。”

对“我的笔记里记录了什么”，这个约束有价值；对“解释 Python 的装饰器”，即使模型本来能解释，没有本地资料时也被同一条规则限制。

原项目没有参考资料时使用的 `main_prompt.md` 明确允许“基于你的知识直接回答用户问题”；有资料时则使用另一份参考资料提示词。两种场景的处理不同。

合理的改进是区分普通解释、用户私有资料问题、需要实时信息的问题。普通解释可以使用模型知识；私有资料必须有证据；实时问题需要有效外部来源。不能把所有情况都改成自由发挥，否则可能把推测说成用户笔记里的内容。

### 生成答案时，预算有限，也无法继续查资料

复刻版 `app/services/deepseek_client.py` 的 `stream_chat` 默认 `max_tokens=700`，聊天入口没有覆盖它。token 是模型的计量单位，不等于汉字数；但这一预算会限制长解释。收到 `finish_reason=length` 时，客户端会抛出异常，聊天服务再返回未完成提示。

该客户端还显式发送 `thinking: disabled`；原项目对话模型构造处没有发送这个显式参数。仅凭代码不能判断服务端默认模式，也不能断言启用思考必然更好。应先修复输入丢失，再对复杂任务验证模式、成本和延迟。

原项目 Agent 的工具列表包含 `search_rag`，可以针对缺少的角度补查。复刻版最终 `stream_chat` 请求只包含消息，没有工具定义；它拿到的是已经整理完的资料包，无法在作答途中主动继续检索。

### 证据整理也有损失信息的风险

复刻版混合检索把 Chunk 转为结果时，`source_id` 使用文档或笔记 ID。后续 `collect_evidence` 又按 `(source_kind, source_id)` 去重。同一份文档的不同段落可能因此只留下一个片段。若答案需要文档前后两部分的信息，模型可能只看见其中一部分。

此外，混合检索的排名分、图证据固定分和网页固定分被直接混排，它们并不是同一种相关性刻度。它们的大小未必代表证据对当前问题的真实价值。这个问题需要用实际检索样本衡量，不能仅凭代码断言某一次回答因此失败。

## 3. 已验证的内容与后续修复顺序

本次完成了两套聊天入口、提示词、模型客户端、历史服务、工具图和检索服务的源码对比，并选择性读取了不含秘密的模型配置字段。

模拟执行当前工具图并捕获聊天服务最终构造的模型消息，得到：工具日志有真实模拟结果，最终 tool_result 为 None；模型消息只有两条，工具结果被写为“无”，历史没有传入。这是对当前代码行为的复现，不是猜测。

本次没有做两套线上服务的同题回答评测，没有检查真实用户资料和索引数量，也没有修改业务代码。因此，具体某一条回答有多大改善，仍需修复后使用相同问题、相同资料对比。

建议按以下顺序实施：

1. **接通对话历史。** 在用户权限范围内读取历史，限制长度后传入回答模型；工具决策和检索规划也应能理解追问指代。
2. **保留完整有效工具结果。** 最终回答使用本轮成功的 observations；停止决策不能覆盖已获得的业务事实。增加“查到结果后结束仍能回答”的验证。
3. **区分问题类型。** 普通知识允许直接解释，私有资料依赖证据，实时问题要求有效搜索结果。
4. **设置合理回答预算。** 把长度变成配置，按任务调整，并明确处理截断。增加 token 数不会自动补回缺失的历史。
5. **把补充检索接入回答决策。** 对新角度补查设置次数、重复查询和超时限制，保留来源。
6. **改善证据选择。** 保留 Chunk 身份，在避免重复的同时保留同一文档中的互补段落；统一融合策略后再验证排序质量。

验收问题可以固定为：“比较 MySQL 和 Redis”后追问“第二个适合存什么”；“今天回顾什么”；没有本地资料时“解释装饰器”；最后用一份需要跨段落取证的文档提问。分别验证记忆、工具事实、普通解释和证据完整性，才知道改动改善了哪一部分。
