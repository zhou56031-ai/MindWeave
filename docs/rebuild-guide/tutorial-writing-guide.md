## 1. 每篇教程必须让读者知道什么

读完一篇教程，读者应能明确回答：

1. 这次要给项目增加什么能力？
2. 应该进入哪个目录，新建哪些文件夹？
3. 每个文件叫什么、放在哪里；新建文件填什么代码，已有文件改哪几处？
4. 每个文件负责什么，为什么在这里创建？
5. 关键后端代码怎样接收数据、调用其他模块、改变状态、产生结果？
6. 怎样运行，看到什么才算成功，失败时从哪里查？

正文按实际操作顺序组织。先给当前任务和文件清单，然后带着读者逐个文件实现；新知识在对应代码出现时解释。

## 2. 按有基础的学习者讲解

用户已自述掌握原第 02–04 章讲授内容：Python 数据结构、函数、模块、类、类型标注、异常、HTTP、JSON、协程及异步任务基础。直接在代码中使用这些知识。

后端讲解的篇幅放在项目开发中的新内容，例如：

- 路由如何被注册，请求最终落到哪个函数。
- 请求模型如何验证输入，业务服务为什么与路由分开。
- 数据库会话由谁创建，什么时候提交，失败时怎样回滚。
- 用户身份怎样传递，查询如何限制到当前用户。
- 笔记保存后，标签、向量和图谱处理怎样衔接。
- 工具、检索、模型调用与后台任务的状态怎样变化。

“未评估”只表示尚无反馈，不自动触发从零开始的理论课。新机制在当前文件中解释到足以完成这一步；用户追问时再深入。

前端直接从参考提交复制到复刻目录，由助手完成必要的本地适配、安装和验证。不再生成前端逐文件操作教程；只记录接入来源、启动方式、验证结果与尚未实现的后端接口。用户单独提问前端知识时再回答具体问题。

## 4. 章节怎样划分

每篇围绕一个能运行、能观察结果的小目标，例如“启动后端并访问健康检查”“保存一篇真实笔记”“读取当前用户的笔记列表”。目标较大时拆成连续小步，每步有明确成果。

开头用几句话说明这一步在完整复刻中的位置，再列出文件变化。主线直接建设正式应用；只有当前功能确实需要时才引入相应机制。独立语法练习和拓展题按需提供，不作为继续复刻的必经条件。

1:1 对齐目标见[复刻路线](roadmap.md)中的参考提交、功能与接口约定。写作前查看对应源码，再决定本步实现，不凭印象设计另一套项目。当前必须简化时明确写出：本步实现什么、和参考版本差在哪里、后续在哪一步补齐；未编写的章节只能标为计划。

## 5. 每篇教程的固定格式

从第 37 篇起，新生成的常规教程**只能有以下三个二级标题**；不得另加第 4 节及以后章节。运行验证、调用链说明、故障边界如确实必要，都写在第 3 节对应操作步骤和整体解释中；不要单列“请求和状态如何穿过文件”“按阶段运行和验收”“配套核验与设计依据”“阶段末核对册”或“逐案推演”。也不要出现逐行代码阅读表。

```text
# 第 XX 篇：这一步完成的具体功能

## 1. 本篇要接通的真实能力
说明业务目标、前置状态与本篇边界，链接对应 Q 技术路线。

## 2. 文件变化和操作顺序
按真实操作顺序列新增依赖、文件与职责。

## 3. 按顺序修改文件与验证
### 步骤 1：【新增文件】或【修改】具体路径
给完整绝对地址；新增文件给完整代码，修改文件只给定位、diff 和生动的整体解释。
按需要继续增加文件步骤，末尾用【运行验证】步骤说明真实观察点。
```

步骤标题只写具体动作，不把“查看”写进步骤。章节结构服务于操作；没有新增依赖或长期服务时不硬加对应步骤，不为了填满篇幅添加无关内容。技术路线 Q 文档也只保留“1 原理、2 同类技术路线对比、3 工程边界”三个二级部分。

## 6. 每个文件必须这样写

### 6.1 先交代位置和用途

每个文件都单独给出：

| 项目 | 必须写清的内容 |
|---|---|
| 执行或编辑位置 | 编辑给出文件完整绝对路径；终端命令给出执行目录完整绝对路径 |
| 目录操作 | 需要先新建哪个文件夹，已有目录是否复用 |
| 文件路径 | 每步给出从 ~ 开始的完整绝对路径，放在独立 text 代码块中供复制 |
| 操作类型 | 新建，或按 diff 定位修改已有文件 |
| 文件作用 | 它负责什么、由谁使用、为什么现在需要它 |
| 变更标记 | 【新增文件】【新增】【修改】【删除】【运行验证】，精确到函数或配置项 |
| 文件内容 | 新建文件给完整代码；修改已有文件只给准确定位和完整改动 diff |
| 后端关键解释 | 对本文件中新增机制和业务逻辑就地解释 |
| 检查方式 | 保存后怎样确认路径、导入或行为正确 |

**具体地址要求（E020）：** 每个新建、修改或删除文件的步骤，紧跟以下格式，路径必须包含实际文件名：

**编辑文件的完整地址：**

```text
./backend/app/core/settings.py
```

标题可保留短相对路径便于辨认，正文地址不使用“复刻根目录中的上述路径”“同上”“自行拼接”、省略号或用户名占位符。文件尚未创建时也给出要创建的精确地址，先创建父目录。终端命令则标明具体目录的完整路径，不把文件路径当作 cd 的目标。

先创建依赖，再创建引用它的文件。写出 import 时，被导入的自建模块必须已经给出；若模块相互配合需一起完成，明确写清完成哪几步后才运行。

### 6.2 新建文件给完整代码，修改文件只给 diff

【新增文件】提供可以直接保存的完整内容。【修改】已有文件时，**只保留“修改定位与前后对照”**：写明完整绝对路径、可搜索的函数名或配置项，再用 diff 展示本次所有需要增删的代码。不要在 diff 后重复贴“完整文件内容”“修改后的完整文件”或整份源码，也不要把标题写成“完整替换”。新增 import、函数、装饰器、配置项和删除位置都要出现在 diff 中，使读者能直接按对照修改现有文件。

新建文件的可复制代码块不含省略号、“其他同上”、尚未定义的类或隐藏依赖。修改文件的 diff 不用 `...` 省略本次变更；新增函数应给出完整函数，必要的 import 也要显示。`+`、`-` 是阅读标记，不复制进源码。

代码与解释对应同一版本，不在代码块外临时补上影响运行的必要步骤。工具生成的 uv.lock、构建产物等只给生成命令和检查方式，不要求手抄。

### 6.3 后端解释紧跟对应文件

每个文件写完后立即解释其中真正影响行为的关键代码，再进入下一个文件。修改已有文件时，把解释紧接在 diff 后，使用一段连贯的整体说明：以一个贴合业务的比喻引入，再连起新增代码与原有文件、请求或启动流程。不要按新增行逐条拆解，也不要把同一机制拆成多个小标题。解释应在叙述中覆盖：

- **触发点**：谁执行到这里，注册阶段还是请求处理阶段？
- **输入**：值从请求、配置、数据库还是调用方传入？
- **动作**：调用谁，为什么需要这一步，等待的是什么？
- **结果**：返回了什么、改变了什么状态、交给下一层做什么？
- **失败**：本步涉及的实际错误如何处理，失败后还会执行哪些动作？

**禁止使用“关键代码逐行阅读”表格。** 不按最终文件行号罗列代码，也不生成“行｜代码定位｜作用与执行时刻”这类表格。尤其不要为 `import`、`class`、`def`、装饰器、赋值、`return` 批量填入“引入函数”“定义动作”“结合前后行阅读”等可套在任何文件上的解释。这些内容占篇幅，却没有说明本项目为什么这样写。行号会随修改失效；需要定位改动时，使用可搜索的函数名、字段名和已有的 diff 标记。

解释应选择本篇最关键的两三处行为，直接引用短代码片段或函数名，在段落里说清真实数据如何经过它们。例如模板列表路由，不必分别解释 `APIRouter` 和 `Depends` 的语法；应说明请求进入 `/note-template/list` 后，`get_current_user_id` 先确认令牌并取得用户编号，`get_db` 提供本次请求的会话，服务层用用户编号限制查询，最后路由把模板数据交给 `success_response`。如果一个文件只有包声明或简单导入，写清文件职责即可，无需硬凑“关键代码”说明。

已经掌握的基础语法不逐行翻译。比如服务方法调用应讲“把当前用户编号交给查询，使结果限定在该用户范围”，而不是再解释参数或函数是什么。

### 6.4 文件增删改查必须重点标记

这是用户明确要求（E013）。凡是新增、修改或删除文件及其内容，都要让读者一眼找到“哪个文件、哪一处、怎样变化”。采用以下统一标记：

| 标记 | 用法 | 必须交代什么 |
|---|---|---|
| 【新增文件】 | 整个文件首次创建 | 准确路径、用途与完整内容 |
| 【新增】 | 已有文件中加入代码 | 插入位置、前后定位原文、新增代码与作用 |
| 【修改】 | 替换已有代码 | 原代码、新代码、替换范围及行为变化 |
| 【删除】 | 删除一段代码或整个文件 | 原代码或文件路径、删除原因，以及是否需要同步调整引用 |
| 【运行验证】 | 执行编译、接口请求或数据库验收 | 写出可运行命令、执行目录与预期结果；纯阅读不列为编号步骤 |

修改已有文件时，固定顺序为：

1. **本次变更清单**：按文件列出标记、函数或配置项、改动内容和原因。多处变化用 C01、C02 编号，一处变化直接标记即可。
2. **定位原代码**：给出可搜索的函数名、字段名及必要上下文。行号只能辅助定位，不能作为唯一依据。
3. **修改前后对照**：用 diff 代码块突出删除和新增行；展示完整的本次改动与足够的上下文，不展示整份修改后的文件。
4. **整体解释**：紧跟 diff，用一段连贯、具体而生动的话解释新增代码怎样与旧代码协作：什么请求或启动动作触发它，数据怎样交接，状态何时变化，失败时会怎样。选择一个贴切比喻后立刻对应回真实函数；不要逐行翻译，也不要把一段代码拆成数段互不相连的套话。
5. **验证**：给出与本次行为变化直接相关的检查，未变部分只交代必要上下文。

**diff 是阅读对照，不是可直接保存的源码。** `-` 表示删除的旧行，`+` 表示新增的新行，替换操作通常由一删一增组成；这些前缀不要复制进项目文件。颜色由阅读器决定，文字标记和正负号仍需清楚。

下面沿用第 8 节入口文件作格式示范，仅说明如何突出改动，不代表本次已修改复刻项目。

**文件：`backend/main.py`。本次变化：【修改 C01】健康检查响应新增 version 字段。**

**编辑文件的完整地址：**

```text
./backend/main.py
```

定位 `health` 函数，前后对照如下：

```diff
 def health() -> dict[str, str]:
-    return {"status": "ok"}
+    # 【修改 C01】响应中增加固定版本标记，方便核对当前运行的代码。
+    return {"status": "ok", "version": "0.1.0"}
```

**整体解释：** 可以把 `/health` 看作服务递给监控的一张小卡片。以前卡片上只有 `status`；现在同一个请求仍进入 `health()`，只是在返回前多写了 `version`，FastAPI 再把整张卡片转成 JSON。客户端会同时收到 `status` 和 `version`；这里的版本是代码写定的值，不会自动读取 Git 提交。验证时请求一次 `/health`，检查响应里确实多了 `"version":"0.1.0"`。

在允许注释的源码中，可紧贴变更行使用合法注释，如 Python 的 `# 【新增】`、`# 【修改 C01】`，与文档清单对应；不能把加粗符号或 diff 前缀写进可运行源码。JSON 等不允许注释的格式只在外部清单和 diff 中标记，保持最终文件有效。

删除的代码在对照中完整标出，最终文件不保留待删除代码或大段注释掉的旧实现。删除整个文件时同步列出受影响的 import 和调用方。跨文件移动明确写出源文件删除位置与目标文件新增位置。

后续步骤只突出本步变化，清理已失去教学用途的旧变更标签，避免标记越积越多。纯阅读或搜索只能放在操作前的简短依据、解释或验收说明中，不单独编号为步骤；也不伪造改动。

## 7. 生动解释怎样落到代码

先选本步真实输入，再追踪它经过哪些文件。比喻用于解释新的职责分工，并立即对应回代码；避免一长段比喻后仍不知道实际调用关系。

例如，讲保存笔记时可以写：

> 请求模型像收件检查台，先看材料是否满足字段要求；路由把合格材料交给笔记服务；服务组织数据库写入。在代码里，真正负责落库的是数据库操作与事务提交。路由返回“保存成功”需要建立在本步约定的写入成功之后。

随后必须用本章确实存在的函数名和输入字段逐步说明，例如标题如何被验证、用户编号从哪里来、提交发生在哪里。没有实现数据库的步骤不使用“已经落库”的描述。

对 commit、异步任务、检索等有边界的机制，说明比喻没有覆盖的关键事实。尤其区分内存状态与持久化、任务被安排与任务完成、接口成功与检索质量达标。

## 8. 文件级操作与解释示范

以下示范展示后端教程的颗粒度，仅用于说明写法。本次更新指导文档不会替读者创建以下应用文件，也不代表整个项目已经实现；正式下一篇应核对实际状态后给出完整步骤。

### 步骤 1：在 backend 下创建 app 文件夹

**执行位置：终端中的复刻根目录。**

```bash
cd "./backend"
mkdir -p app
```

`app` 存放后续共享工具、路由和业务模块，应用入口 main.py 与它并列放在 backend 下。这里展示创建包的格式；正式新教程会在包里创建具体的响应工具和路由。

### 步骤 2：在 app 中新建 __init__.py

**操作类型：新建文件。**

**编辑文件的完整地址：**

```text
./backend/app/__init__.py
```

**作用：** 将 app 作为明确的 Python 包组织，供后续业务模块导入；启动命令直接导入 backend 下的 main.py。

```python
"""RAGNotebook 复刻项目的后端应用包。"""
```

这个文件暂不放初始化业务。它不会自动启动 HTTP 服务。

### 步骤 3：在 backend 中新建 main.py

**操作类型：新建文件。**

**编辑文件的完整地址：**

```text
./backend/main.py
```

**作用：** 创建 FastAPI 应用对象，注册一个健康检查入口，供后续启动器导入。

```python
from fastapi import FastAPI

app = FastAPI(title="RAGNotebook Rebuild")


@app.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok"}
```

**关键代码怎样配合：**

`app = FastAPI(...)` 创建承接路由和请求处理的应用对象。可以把它看作后端的接待总台；后面的路由规则要登记到同一张接待表上。

`@app.get("/health")` 在模块加载时登记一条规则：收到匹配的 GET 请求时，将请求交给 health 函数。登记规则时不会立即执行一次健康检查。

`health()` 返回字典后，FastAPI 将它转换为 JSON 响应。`{"status": "ok"}` 是这里自行定义的简单健康标记，只能说明该入口可响应；本例没有检查数据库或模型是否可用。

### 步骤 4：启动后验证这个文件

**执行位置：终端 A，复刻项目 backend。**

```bash
uv run uvicorn main:app --reload --host 127.0.0.1 --port 8100
```

`main:app` 前半部分让启动器导入当前 backend 下的 main 模块，冒号后指定其中的应用对象。Uvicorn 负责监听端口、接收 HTTP 请求，再把请求交给这个对象。导入路径和文件名需要对应，不能把其他项目的启动命令直接搬来。

终端 A 保持运行；在**新终端 B 的任意目录**验证：

```bash
curl -i http://127.0.0.1:8100/health
```

预期 HTTP 状态码为 200，响应正文为：

```json
{"status":"ok"}
```

一次请求的路径是：浏览器或 curl → Uvicorn → app 中已登记的 GET /health → health 函数 → 字典转换为 JSON → 客户端收到响应。

在终端 A 按 Control + C 停止服务。首次验证失败时，先看终端 A 的启动错误，再检查当前目录和 main 的导入路径。

## 9. 环境、依赖和命令规则

## 12. 技术路线必须配套独立 Q 文档

当教程**首次实际引入**一条可独立选择的技术路线（例如数据库、Web 框架、认证方式、解析/切片或检索方式），同时在 `docs/rebuild-guide/chapters/technology-routes/` 新建或链接一篇 Markdown 文档。文件名固定以大写 `Q` 开头，采用 `Q01-short-topic.md` 这样的两位序号与短主题名；序号持续递增，不随教学篇号重置。同一路线在多篇出现时复用已有 Q 文档，关键实现改变时更新比较和项目现状。

每篇 Q 文档应包含：本项目在**哪个具体文件或函数**用到它；一次真实数据或请求怎样经过这项技术；核心原理与失败边界；至少两条同类可选路线的公平对比（解决的问题、优势、代价和适用场景）；本项目为什么采用当前路线、它与参考项目是否一致；可供进一步核对的官方或规范来源。把“本项目因复刻而沿用”与“新项目一般如何选”分开写，避免把框架偏好写成性能或安全性的绝对结论。涉及会变化的技术细节时先核对官方资料，不照抄未经验证的版本、速度或兼容性结论。

技术路线首次出现的操作章节给一条 Q 文档链接，并在[Q 文档目录](chapters/technology-routes/README.md)登记。Q 文档只放原理和比较，不重复整份代码、逐行表格或文件操作步骤；章节继续承担完整路径、增删改 diff 和验证。未来计划中的路线在真正引入时创建，不把 Q 文档的存在当成正式后端功能已实现。Q 文档不是用户知识掌握证明，学习画像仅按用户反馈更新。

## 14. 工程面试视角：解释设计与特定情况

后续教程讲完本步的真实请求链路后，增加一小段**工程面试思考**。面试官关心的不是“你会调用哪个函数”，而是为什么采用当前设计、它付出什么代价、真实流量或故障下会怎样。围绕本篇最关键的设计提出两三个具体问题，并给出结合当前代码的回答；不要用脱离项目的背诵式八股题，也不要把同一段代码拆成逐行问答表。

回答至少覆盖适用的三个层次：第一，当前需求和约束是什么，为什么选择这条路线，其他可选路线的收益与代价在哪里；第二，一个特定场景发生时，现有代码会产生什么可观察结果，例如重复请求、并发冲突、客户端断开、数据库故障、用户越权或大文件；第三，当前方案的边界是什么，如果业务规模或可靠性要求变化，应改哪一层、用什么机制验证改动。只讨论本篇真正涉及的情形，明确区分已实现、已验证和未来改进。

技术路线的完整原理与同类比较仍放在独立 Q 文档；操作篇的面试思考只引用其中与本步代码直接相关的取舍。不要重新加入“逐案推演：输入、经过、结果”、逐行表格或阶段末完整代码核对册。
